# 設計判断

要件定義で未決だった項目を、実装にあたって次のように決めました。

## 技術スタック

| 領域           | 採用                                               | 理由                                                                                        |
| -------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 言語           | TypeScript(全体)                                   | フロントとサーバーでマージ・機密検出・ビューのロジックを共有できる(`packages/core`)         |
| 実行環境       | Cloudflare Workers(推奨)/ Node.js 22               | サーバー管理なしで無料枠から動かせる。Web標準APIだけで書き、同じコードをNode.jsでも動かす   |
| バックエンド   | Hono                                               | 軽量、Web標準のRequest/Responseで書けてMCP SDKのWeb標準トランスポートと相性がよい           |
| DB             | Cloudflare D1 / SQLite(better-sqlite3)             | どちらもSQLite方言。FTS5のtrigramで日本語全文検索ができる                                   |
| ノートの保存   | DB内のGitオブジェクト / GitHub Git Data API        | 下記「ノートの保存先」                                                                      |
| 認証           | @simplewebauthn/server                             | パスキーの定番実装                                                                          |
| MCP            | 公式 TypeScript SDK(Streamable HTTP、ステートレス) | OAuthの保護リソースとして動かしやすい                                                       |
| フロントエンド | React + Vite + vite-plugin-pwa                     | PWA(オフライン、共有ターゲット)を素直に作れる                                               |
| エディタ       | CodeMirror 6                                       | Markdownがそのまま正のデータなので、WYSIWYGではなくプレーンテキストエディタ。スマホでも軽い |

## ノートの保存先

当初はサーバー上のGitリポジトリ(git CLI)に保存していましたが、次の理由で変更しました。

- Cloudflare Workers ではファイルシステムもgitコマンドも使えない
- 複数の人が使うサービスにすると、ユーザーごとのリポジトリをサーバーのディスクで管理することになり、運用が重い

そこで「Gitの意味でノートを保存する」インターフェース(`NoteStore`)を作り、ユーザーが保存先を選べるようにしました。

- **このサービス内**:Gitと同じ形式のオブジェクトをデータベースに保存する(何も用意しなくても使える)
- **自分のGitHub**:GitHub API で自分のリポジトリに本物のコミットを作る(ノートを自分の管理下に置ける)

どちらでも、履歴・作成者・提案ブランチ・マージコミットという「GitHubのような」モデルは同じです。Obsidianでサーバー上のフォルダを直接開く使い方はやめました(GitHub保存なら、cloneしたリポジトリを開けます)。

同時書き込みはプロセス内のロックではなく、ブランチ更新の compare-and-swap と再試行で扱います(Workersでは同じユーザーのリクエストが別のインスタンスで処理されるため)。リアルタイム通知も、接続を張り続けるSSEではなく軽いポーリングにしました。

プラグイン(サーバー内で任意のコードを動かす仕組み)は、複数人で使うサービスでは安全に提供できないため廃止しました。

## 段落(ブロック)単位の差分・マージ

- Markdown本文を「ブロック」の列に分割する独自の軽量パーサー(見出し・段落・リスト項目・コードブロック・引用・表)。ブロックは元の文字列(後続の空行を含む)を保持し、連結すると元の本文に完全に戻る。
- ブロックの比較キーは前後の空白を除いたテキスト。
- LCSによる二者diffを2本とり、diff3で統合。重なる変更だけを競合にし、隣接する段落の変更は競合にしない(行単位のgitより競合が少ない)。
- フロントマターはYAMLをパースしてキー単位で三方向マージ。

## スマホでの使い方の優先順位

1. **メモ(入力)**:起動直後に書く画面、クイックキャプチャ(Inboxの日付ノートへ追記)、共有シート、iOSショートカット
2. **読み返し**:最近のノート、検索、ノートに質問、バックリンク
3. **タスク・DB**:スマホではリスト/カード表示のみ。複雑なDB操作は「AIに頼む」で代替

## アプリ名

正式名は未定のため、リポジトリ名に合わせて「Ganesya AI Memo」(CLI名 `gmemo`)を仮称としています。表示名は `GMEMO_RP_NAME` で変えられます。

## その他

- AIポリシーの初期値は「ローカルLLMのみ」。外部AIエージェントには、ユーザーが明示的に許可したフォルダだけが見える。
- 外部エージェントに渡すときのマスキングは、値のフィンガープリントから作る安定した置換文字列(`[SECRET_xxxxxxxx]`)にし、書き戻されたときに元の値へ戻す。これでエージェントがノートを編集しても機密値が壊れない。
- 埋め込みの外部送信はしない(ローカルモデルか内蔵ベクトルのみ)。
