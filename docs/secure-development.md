# ソースコードのセキュリティ方針

このアプリのソースコードと依存ライブラリを安全に保つための方針です。運用(環境、シークレット、監査ログ、インシデント対応)は [運用方針](operations.md) にあります。

## 考え方

「セキュリティホールがない」ことは証明できません。代わりに、次の4つをすべて仕組みにして、台帳で追えるようにします。

| 段階     | やること                                             | 仕組み                                                        |
| -------- | ---------------------------------------------------- | ------------------------------------------------------------- |
| 入れない | 危ない書き方をできなくする、新しい入口は設計時に確認 | ESLint のセキュリティルール、コーディング規約、脅威・対策台帳 |
| 見つける | 依存ライブラリの脆弱性とコードの穴を早く見つける     | npm audit(毎回+毎週)、CodeQL、Dependabot、定期の総点検        |
| 直す     | 深刻度に応じた期限内に直す                           | 脆弱性対応台帳、期限切れで CI が失敗する                      |
| 記録する | 何が見つかり、どう判断し、いつ直したかを残す         | `security/` の台帳(Git の履歴がそのまま監査証跡になる)        |

## 台帳(`security/`)

| 台帳                                                       | 内容                                                                                                     |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| [`vulnerabilities.yaml`](../security/vulnerabilities.yaml) | **脆弱性対応台帳**。依存ライブラリの脆弱性(GHSA / CVE)と実装起因の脆弱性(`GM-年-番号`)を全件。判断と期限 |
| [`dependencies.yaml`](../security/dependencies.yaml)       | **依存ライブラリ台帳**。直接依存の用途とリスク区分。間接依存は CI が作る SBOM(CycloneDX)                 |
| [`threats.yaml`](../security/threats.yaml)                 | **脅威・対策台帳**。起こりうる穴、防いでいる仕組み、それを確かめるテスト                                 |

`npm run security:check`(CI でも毎回実行)が、台帳と実際の状態を突き合わせます。次のときに失敗します。

- `npm audit` が報告した脆弱性が台帳にない
- 台帳で「修正済み」なのに、まだ報告されている
- 対応中の項目が期限を過ぎた、リスク受容の見直し期限を過ぎた
- 直接依存が台帳にない、または台帳にあって実際にはない
- 脅威・対策台帳に書いたテストが見つからない(名前を変えた、消した)

台帳の変更は通常のコード変更と同じくコミットし、レビューします。

## 1. 依存ライブラリ

### 追加するとき

新しい依存を入れる前に確認し、`dependencies.yaml` に用途とリスク区分を書きます。

- [ ] 自分で書ける小さな処理ではないか(依存は少ないほど安全)
- [ ] 保守されているか(最近のリリース、Issue への対応)、利用者が十分いるか
- [ ] インストール時にスクリプトを実行しないか(`postinstall` など)
- [ ] ライセンスが MIT など問題のないものか
- [ ] 本番に含まれるか(`dependencies` か `devDependencies` か)

リスク区分が `high`(認証、暗号、外部からの入力の解釈、HTMLの描画)のものは、特に慎重に選び、更新時は変更内容を読みます。

### 更新

- **Dependabot** が毎週月曜に更新のPRを作ります。開発用ツールのマイナー・パッチ更新はまとめて、本番の依存は1つずつです。GitHub Actions と Docker のベースイメージも対象です。
- 本番の依存のメジャー更新は、リリースノートの破壊的変更とセキュリティ関連の項目を読み、[運用方針](operations.md) の流れ(ステージング → 本番)で出します。
- `package-lock.json` を必ずコミットし、CI とデプロイは `npm ci`(ロックファイルどおり)で入れます。
- CI で `npm audit signatures` を実行し、パッケージが npm レジストリの正規のものかを確かめます。
- GitHub Actions はタグではなくコミットSHAで固定します(タグは書き換えられるため)。

## 2. 脆弱性(CVE)への対応

### 見つける経路

| 経路                        | いつ                                     |
| --------------------------- | ---------------------------------------- |
| `npm audit`(security:check) | push・PRごと、毎週月曜(新しい公開を拾う) |
| Dependabot alerts           | 公開され次第(GitHub が通知)              |
| CodeQL(security-extended)   | push・PRごと、毎週                       |
| 定期の総点検(下の5)         | 四半期ごと                               |
| 外部からの報告              | 随時([SECURITY.md](../SECURITY.md))      |

### 対応期限

見つけた日から数えます。`scope` は、その脆弱性のあるコードがどこで動くかです。

| 深刻度   | 本番で動く(production) | ビルド・開発のみ(build / dev) |
| -------- | ---------------------- | ----------------------------- |
| critical | 3日                    | 30日                          |
| high     | 7日                    | 30日                          |
| moderate | 30日                   | 90日                          |
| low      | 90日                   | 次の定期更新                  |

本番で動く critical / high は、ほかの作業より優先し、修正をすぐステージング → 本番に出します。

### 手順

1. **登録**:`vulnerabilities.yaml` に追加(`status: open`、`found`、`due`)。CI が失敗したらまずこれ。
2. **影響の判断**:そのコードは本番に含まれるか。該当する機能を使っているか。攻撃者が届くか。
3. **決める**(どれも台帳に理由を残す):
   - `fixed`:更新・修正した(`closed` と `resolution`)
   - `not-affected`:影響しない(`reason` 必須。例:該当する関数を使っていない)
   - `accepted`:今は直さないことを受け入れる(`reason` と `review_by` 必須。期限を過ぎると CI が失敗する)
4. **出す**:本番に関わるものはステージングで確認してから本番へ。

## 3. 実装起因の穴を作らない

### 設計するとき

新しい**入口**を作るときは、`threats.yaml` に行を足し、何から守るか・どう守るか・どのテストで確かめるかを先に決めます。入口とは:

- 新しいAPI・MCPツール(特にAIエージェントが呼べるもの)
- サーバーから外部への通信
- 新しく保存するデータ(サーバー、ブラウザ)
- 公開URL(カレンダーのフィードなど)

### コーディング規約

このアプリで実際に起きた・起きやすい穴から作った規約です。カッコ内は関連する台帳の項目です。

1. **アカウントの分離**:`user_id` は必ずセッションかトークンから取り、すべてのクエリを `user_id` で絞る。リクエストの値を `user_id` に使わない。(T-01)
2. **エージェントに見せるものは `AgentOps` を通す**:エージェント(`principal`)が呼べるAPIは、必ずフォルダ制限・AIポリシーの確認(`canSee`)と伏せ字(`outgoing`)を通す。生のデータを返す新しい経路を作らない。(T-05、GM-2026-002)
3. **パスは正規化してから確認し、確認したパスを使う**:確認と読み込みで別の書き方を使わない。(GM-2026-003)
4. **SQLに値を埋め込まない**:値は `?` で渡す。コード内で組み立てた固定のSQL断片は名前を `…Sql` にする(ESLint が強制)。(T-14)
5. **HTML は DOMPurify を通したものだけ**:`dangerouslySetInnerHTML` は `lib/markdown.ts` の出力(またはエスケープ済みの文字列)だけに使う。(T-10)
6. **サーバーからの外部通信は検証してから**:URL を検証し、リダイレクトは手動で追って毎回検証、受け取る大きさに上限を付ける。(T-08、GM-2026-006)
7. **秘密を出さない**:トークン、コード、パスワード、ノートの本文をログ・エラーメッセージ・セキュリティログに出さない。トークンやコードの比較は定数時間で。
8. **端末に残すデータは消去の対象に入れる**:ブラウザに保存するものを増やしたら `lib/localData.ts` の消去対象に加える。(T-11、GM-2026-001)
9. **迷ったら閉じる(fail closed)**:設定がない、検証できない、想定外の値のときは拒否する。
10. **`eval` 系を使わない**:`eval`、`new Function`、`javascript:` URL は ESLint で禁止。

### テスト

- 脆弱性を直したら、**必ず回帰テストを足し、修正前のコードで失敗することを確かめる**。テストは `threats.yaml` に書く。
- アカウントの分離、エージェントの権限、認証は、新しいAPIごとに「他人・権限のないエージェント・未サインインで拒否されること」をテストする。

### レビュー

- PR のチェックリスト(`.github/pull_request_template.md`)を埋める。
- 1人で開発していても、PR ごとに Claude Code の `/security-review` か `/code-review` を実行し、指摘は台帳に登録してから直す。
- CI(lint、型チェック、テスト、security:check、CodeQL)が通らない PR はマージしない。

## 4. 静的解析

| ツール                              | 見ているもの                                                      |
| ----------------------------------- | ----------------------------------------------------------------- |
| ESLint `gmemo/no-sql-interpolation` | SQL への値の埋め込み(`eslint/gmemo-rules.js`)                     |
| ESLint `no-eval` ほか               | 文字列からのコード実行                                            |
| TypeScript(strict)                  | 型の取り違え                                                      |
| CodeQL(security-extended)           | XSS、インジェクション、SSRF、パストラバーサル、安全でない乱数など |

## 5. 定期の総点検

**四半期ごと**に、コード全体を対象にした点検を行います(Claude Code のサブエージェント、または外部のレビュー)。重点は台帳の脅威の分類(アカウントの分離、認証、エージェントのポリシー、インジェクション、SSRF、XSS、暗号)。見つかったものは `GM-年-番号` で台帳に登録し、上の期限で対応します。点検した範囲と「問題なし」と判断した箇所も、`threats.yaml` の `reviewed` を更新して残します。

### 初回の点検(2026-10-11)

| 種類           | 件数 | 結果                                                                               |
| -------------- | ---- | ---------------------------------------------------------------------------------- |
| 依存ライブラリ | 14   | すべて修正(開発・ビルド用ツールのみ。本番の依存には 0 件)                          |
| 実装起因       | 14   | 11件修正(high 2件を含む)、2件対応中(low)、1件リスク受容(low)。014 は CodeQL が検出 |

詳細は `security/vulnerabilities.yaml` の `GM-2026-001`〜`014`。

## 6. GitHub 側で有効にする設定

手順は [GitHub リポジトリの設定手順](github-setup.md) にあります。要点は次のとおりです。

- アカウントの2段階認証、デフォルトブランチを `main` に
- Actions の権限を読み取りのみに、外部からのPRのワークフローは承認制に
- Dependabot alerts / security updates、Secret scanning と Push protection、Private vulnerability reporting
- `main` をルールセットで保護し、`check`、`security`、`docker`、`analyze`(CodeQL)の成功と、CodeQL の重大な警告がないことを必須にする

## 7. 脆弱性の報告

[SECURITY.md](../SECURITY.md) を見てください。報告を受けたら、`source: report` で台帳に登録します。
