# 運用方針

情報漏洩を防ぎ、起きたときに「何が・いつ・誰によって」を後から確かめられるようにするための運用ルールです。Cloudflare Workers での運用を前提にしています(セルフホストでも考え方は同じです)。

## 1. 環境

| 環境                  | Worker      | D1          | 誰が使えるか                                 | 新規登録                | デプロイ                   |
| --------------------- | ----------- | ----------- | -------------------------------------------- | ----------------------- | -------------------------- |
| 本番(production)      | `gmemo`     | `gmemo`     | 利用者                                       | `invite`(招待制、既定)  | `npm run deploy:prod`      |
| ステージング(staging) | `gmemo-stg` | `gmemo-stg` | **運用者本人だけ**(Cloudflare Access で制限) | `closed`(管理者1人のみ) | `npm run deploy:stg`       |
| 開発(development)     | `gmemo-dev` | `gmemo-dev` | ローカル / 試験用                            | `closed`                | `npx cf deploy`(mode なし) |

- 環境ごとに **Worker・データベース・シークレットをすべて分けます**。ステージングに本番のデータやシークレットを持ち込みません(本番データでの確認が必要なときは、ダミーデータを作る)。
- `--mode` を付け忘れたデプロイは `gmemo-dev` に向かうので、本番を誤って上書きすることはありません。
- ステージングは Cloudflare Access の通過が必須です。Access の設定がないとアプリ自身が全リクエストを拒否します(fail closed)。検索エンジンに載らないよう `X-Robots-Tag: noindex` を付け、画面の上部に「STG」の帯を出します。
- ステージングと本番では、パスキーのドメインが違うので、それぞれでアカウントを作ります。

## 2. リリースの流れ

1. `main` から作業ブランチを切り、変更を入れる
2. ローカルで確認:`npm run lint && npm run typecheck && npm test && npm run build`
3. ステージングへ:`source deploy.env && npm run deploy:stg`(リポジトリの一番上で)
4. ステージングで確認(下のチェックリスト)
5. 本番へ:`npm run deploy:prod`(`main` の、CI が通ったコミットからだけ実行できる。[手順](deploy-cloudflare.md#8-本番にデプロイする))
6. 本番の **設定 → セキュリティログ** で、デプロイ直後にエラーや拒否が増えていないかを見る

ステージングで確認すること:

- [ ] サインイン(パスキー)・サインアウトができる
- [ ] ノートの作成・編集・検索・履歴が動く
- [ ] セキュリティログに今の操作が記録され、「改ざんチェック」が問題なしになる
- [ ] (データベースの変更を含むとき)マイグレーションが最初のリクエストで通る

問題が出たら:前のコミットに戻して再デプロイするか、ダッシュボードの Workers & Pages → 対象のWorker → Deployments(または `npx wrangler rollback --name gmemo`)で1つ前のバージョンに戻します。データベースは D1 Time Travel で過去30日の任意の時点に戻せます。

## 3. アクセス権の管理

- **Cloudflare アカウント**:2段階認証(できればセキュリティキー / パスキー)を必須にする。メンバーを増やすときは最小限のロールで。
- **API トークン**:デプロイに使うトークンは「Workers Scripts:Edit」「D1:Edit」など必要な権限だけ、対象アカウントだけに絞り、期限を付ける。CIに置く場合はリポジトリのシークレットに入れ、ログに出さない。
- **ステージング**:Access のポリシーは「自分のメールアドレスだけを許可」。他の人を足さない。
- **GitHub**:`main` は保護ブランチにし、直接 push しない。
- **アプリの管理者**:管理者アカウントはノートを読めませんが、アカウント削除やリカバリーコードの再発行ができます。管理者は最小人数にし、パスキーを2つ以上(端末とセキュリティキーなど)登録しておく。

## 4. シークレットの管理

| シークレット                | 用途                                             | 環境ごと |
| --------------------------- | ------------------------------------------------ | -------- |
| `GMEMO_SETUP_TOKEN`         | 最初の管理者アカウントの作成(作成後は使われない) | 別の値   |
| `GMEMO_SECRET_KEY`          | GitHub トークンの暗号化、セキュリティログの署名  | 別の値   |
| `GMEMO_SECRET_KEY_PREVIOUS` | 鍵の入れ替え中だけ使う(下記)                     | -        |

- シークレットは `npx cf workers secrets update` で Worker に直接設定し、リポジトリ・チャット・Issue・設定ファイルに書きません。
- 生成は `openssl rand -base64 32` など、推測できない値で。

### `GMEMO_SECRET_KEY` の入れ替え(年1回、または漏洩の疑いがあるとき)

```sh
cd packages/server
# 1. 今の鍵を「前の鍵」として登録(値はダッシュボードでは見られないので、保管している値を使う)
npx cf workers secrets update GMEMO_SECRET_KEY_PREVIOUS --worker gmemo --text "<今の鍵>"
# 2. 新しい鍵にする
npx cf workers secrets update GMEMO_SECRET_KEY --worker gmemo --text "$(openssl rand -base64 32)"
```

- 入れ替え後も、古い鍵で暗号化された GitHub トークンは前の鍵で復号され、使われたときに新しい鍵で暗号化し直されます。
- セキュリティログの改ざんチェックは、新旧どちらの鍵の署名も受け付けます。
- `GMEMO_SECRET_KEY_PREVIOUS` は、古い署名のログが保存期間(既定400日)を過ぎて消えるまで残しておきます。**古い鍵自体が漏れた疑いがある場合**は、すぐに消し、各ユーザーに GitHub 接続の設定し直しを依頼します(古いログの署名は検証できなくなります)。

## 5. 監査ログ(セキュリティログ)

### 何を記録するか

| 分類             | 例                                                                                                               |
| ---------------- | ---------------------------------------------------------------------------------------------------------------- |
| サインイン       | アカウント作成、サインイン(成功・失敗)、リカバリーコード、サインアウト、パスキーの追加・削除                     |
| AIエージェント   | エージェントの作成・変更・無効化、トークンの発行・失効、**ノートの読み取り・検索・書き込み**、拒否された読み取り |
| MCP / OAuth      | クライアント登録、接続の許可・拒否、トークンの発行・更新・失敗、接続解除                                         |
| データの持ち出し | エクスポート、カレンダーの公開URLの作成・無効化、保存先の変更                                                    |
| ポリシー         | AIポリシーの変更、検出結果を「問題なし」にした操作                                                               |
| 管理者           | アカウント削除・リセット、招待の作成・取り消し                                                                   |
| 攻撃の兆候       | 無効なトークン、試行回数の上限、別サイトからの書き込み、Access で拒否されたアクセス                              |

記録しないもの:ノートの本文、AIの検索クエリ、トークンやコードの値(トークンは先頭4文字だけ)。AIが読んだ・書いたノートは**パス**だけを残します。

### どこに残るか

- **D1 の `security_events` 表**:追記のみ。各行にHMAC署名(`GMEMO_SECRET_KEY` から作った鍵)を付けるので、行の書き換えや途中の削除は「改ざんチェック」で検出されます。
- **Workers Logs**:同じ内容をJSON1行で出力します。データベースとは別の場所にコピーが残るので、データベースごと消された場合にも追えます(Workers Logs の保存期間はプランによります)。
- 利用者は **設定 → セキュリティログ** で自分のアカウントの記録を見られます。管理者は全体を見て、改ざんチェックを実行できます。

IPアドレスは既定でハッシュ化して保存します(`GMEMO_AUDIT_IP=hash`、同じアドレスからの操作だと分かるが元のアドレスには戻せない)。インシデント調査のために生のアドレスが必要なら `full`、まったく残さないなら `off` にします。

保存期間は既定で400日です(`GMEMO_AUDIT_RETENTION_DAYS`)。毎日の定期処理で、それより古い記録を削除します(削除したこと自体も記録します)。

### 定期的に見ること

**毎週**(本番の 設定 → セキュリティログ → 「問題のみ」):

- [ ] 心当たりのないサインイン、リカバリーコードでのサインイン
- [ ] `token.rejected` や `security.rate_limited` が急に増えていないか
- [ ] 知らないAIエージェント・MCPクライアントの作成や接続許可
- [ ] AIエージェントによる、普段と違う大量の読み取り
- [ ] エクスポート、保存先の変更、カレンダー公開URLの作成

**毎月**:

- [ ] 管理者で「改ざんチェック」を実行し、問題なしを確認
- [ ] 使っていないエージェント・トークン・招待を失効
- [ ] Cloudflare のメンバーと API トークンを見直す

## 6. 漏洩が疑われるとき

慌てて記録を消さないこと。まず止めて、記録を確保してから調べます。

1. **止める**
   - 該当するAIエージェントを 設定 → AIエージェント で無効化(全トークンが即座に失効)
   - MCPクライアントの接続を解除
   - アカウントが乗っ取られた疑いがあれば「すべての端末からサインアウト」、知らないパスキーを削除、リカバリーコードを再発行
   - 必要なら `GMEMO_SIGNUP=closed` で再デプロイして新規登録を止める
2. **記録を確保する**
   - 管理者で改ざんチェックを実行
   - ログを書き出す:`npx wrangler d1 export gmemo --remote --table security_events --output incident.sql`(セルフホストなら `gmemo audit export --days 90 > incident.jsonl`)
   - Workers Logs の該当期間を保存
3. **調べる**:いつから、どのエージェント・アカウントが、どのノート(パス)に触れたか
4. **元に戻す**:シークレットの入れ替え(上記)、GitHub トークンの再発行、必要なら D1 Time Travel でデータを戻す
5. **知らせる**:影響を受けた利用者に、何が起きて何をしたかを伝える
6. **振り返る**:原因と再発防止策を残す

## 7. バックアップ

- D1 は Time Travel で過去30日まで戻せます(自動)。
- 長期保存が必要なら、月1回 `npx wrangler d1 export gmemo --remote --output backup-YYYYMM.sql` を実行し、暗号化した場所に保管します(バックアップには全ユーザーのノートが含まれるので、扱いは本番データと同じ)。
- GitHub 保存のユーザーのノートは、そのユーザーのリポジトリにあります。
